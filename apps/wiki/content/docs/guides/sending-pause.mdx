Plunk has two separate ways to stop a project from causing harm: **disabling** it and **pausing sending**. They look similar but do very different things, and picking the wrong one during an incident can throw away the data you need to recover.

## Disabling vs. pausing

| | Disabling a project | Pausing sending |
| --- | --- | --- |
| Stops outgoing email | Yes | Yes |
| Blocks incoming API requests (write operations) | Yes | No |
| Event ingestion continues | No | Yes |
| Workflows keep executing | No | Yes |
| Sequences keep progressing | No | Yes |
| Where it's checked | Authentication middleware | Email processor only |
| Toggle | Automatic (billing failure, abuse detection) or support action | Project settings, by any project admin/owner |

**Disabling a project** is an authentication-layer block. It is checked on every authenticated request, so once a project is disabled it stops accepting writes entirely — including the events that would tell you what went wrong. This is the right tool for abuse, fraud, or billing failure, where you also want to stop the source of the problem.

**Pausing sending** is a much narrower brake. It only affects the point where an email would actually be handed to the email processor. Everything upstream of that — the API, `/v1/track`, `/v1/identify`, workflow triggers, sequence enrollment and step advancement — keeps working exactly as before. Nothing is lost, and nothing needs to be replayed once you unpause.

Use the sending pause when you need to stop a bad send (a broken template, a runaway campaign, a workflow that fires more often than intended) while you investigate, and you still need incoming events and workflow/sequence progress to keep flowing so you understand the full blast radius.

## Turning it on

Go to **Settings → General** and toggle **Pause sending**. The change takes effect immediately for any email not yet sent — no redeploy, and no environment variable involved. Because it's a per-project setting, pausing one project in a self-hosted deployment with many projects doesn't affect the others.

## What happens to paused email

Any email that is queued for sending while the project is paused is marked **Suppressed** rather than sent, failed, or cancelled. This is a distinct status from a hard failure: nothing about the email was wrong, and it wasn't dropped — it's held so you can review exactly what would have gone out before deciding whether to unpause.

Suppressed emails are not automatically retried when you unpause. Sends that occur after unpausing go through normally; anything suppressed during the pause stays suppressed as a record of what was held back.

## Unpausing

Toggle **Pause sending** off from the same settings page. Sending resumes immediately for new email — no manual repair step is required.
